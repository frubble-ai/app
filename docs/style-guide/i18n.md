# Internationalization

## Structure

i18n configuration lives at `apps/app/src/i18n/`. The app bundles its translation resources
through Next (English only, a few small files, so not worth a fetch).

```
src/
├── i18n/
│   ├── index.ts              # i18n setup and initialization
│   ├── lib/i18next.d.ts      # every key typed against the English files
│   └── resources/
│       └── en/
│           ├── auth.json
│           ├── home.json
│           └── layout.json
```

Resource files are scoped by domain, mirroring the app's feature structure. There is no catch-all
`common.json`: a string belongs to the domain that shows it. Each file is an i18next namespace
registered in `src/i18n/index.ts`, and a screen loads its own with `useTranslation("auth")`, then
uses keys relative to that file (`t("errors.generic")`).

## Testing

In tests, translations are **never rendered**. The i18n mock replaces every translation call with
its namespace and key path, so tests assert on keys, not translated strings.

```ts
const { t } = useTranslation("auth");

// what renders in the app
t("signIn.submit") → "Sign in"

// what renders in tests: the namespace plus the key
t("signIn.submit") → "auth.signIn.submit"

// with interpolation values, they follow the key as (name=value, …)
t("signIn.welcome", { name: "Ada" }) → "auth.signIn.welcome(name=Ada)"
```

The values let a test see which ones reach the text, without rendering any copy.

This is a mandatory mock. It lives in `src/testing/mocks.ts` alongside global mocks, since every
test suite depends on it.

### Why

- Tests don't break when copy changes
- Assertions are explicit: you see exactly which key is used
- No need to keep test data in sync with translation files
- Tests verify the right key is used in the right place, not that the i18n library works
